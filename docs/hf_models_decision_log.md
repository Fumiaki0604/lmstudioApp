# HuggingFace モデル導入検討ログ

作成: 2026-06-01  
対象プロジェクト: lmstudio 自律会話アプリ

---

## 検討した4モデル

### 1. 感情分析 BERT ✅ 統合済み

**モデル**: `koheiduck/bert-japanese-finetuned-sentiment` (~110MB)  
**追加依存**: `fugashi`, `ipadic`, `unidic-lite`（MeCabベーストークナイザー用）

**入れた理由**
- Hermes Director が recent_log を診断する際、発言ごとの感情トーンを数値で把握できる
- `text_pair` 形式で正確に動作することを確認（例: 「今日はとても楽しかった！」→ POSITIVE 0.995）
- 追加の依存が少なく、MPS（Apple Silicon GPU）で動作

**統合箇所**
- `hermes_director.py` の `_build_prompt()` — recent_log の各エントリに 😊😞😐 アイコンを付加

---

### 2. T5 要約 ❌ 統合見送り

**モデル**: `sonoisa/t5-base-japanese` (~250MB)

**入れようとした理由**
- Hermes Director に渡す古い会話ログをT5で圧縮 → より多くの文脈を少ないトークンで渡せる
- soul.md 更新時に LM Studio への入力を要約で削減

**入れなかった理由（実験結果）**

```
入力: お菓子作りに挑戦したい。ずんだ餅も作ってみたい。リセットっていう考えが好き。
出力: 。お菓子作りに挑戦してみたい。。
```

```
入力: 10ターン分の会話ログ（東北ずん子、雨晴はう、等）
出力: ermes:そうだね。リセット って思ってるんだけど、、。:そうそう。でもね。
```

`sonoisa/t5-base-japanese` はベースモデルであり、会話テキストの要約に特化したファインチューニングがされていない。抽象的な要約ではなく入力の一部を繰り返す傾向があった。

**今後の代替候補**
- ニュース要約特化の fine-tuned T5/mT5 モデルが公開された際に差し替え予定
- `hf_models.py` の `summarize()` 関数はそのまま残してある

---

### 3. Cross-Encoder ❌ 統合見送り

**モデル**: `hotchpotch/japanese-reranker-cross-encoder-xsmall-v1` (~120MB)

**入れようとした理由**
- bi-encoder（GLuCoSE）の境界値（cos類似度 0.50〜0.75）を再判定し、同キャラ繰り返し検出の精度を上げる

**入れなかった理由（実験結果）**

```
そのリセットっていう考えが好きだよ ↔ そのリセットっていう考えが好きだよ！…（ほぼ同文）→ 0.692
今日は楽しかった！              ↔ そのリセットっていう考えが好きだよ（無関係）  → 0.597
天気がいいね                   ↔ ずんだ餅食べたい（無関係）                  → 0.590
おはよう！                     ↔ おやすみ〜（正反対）                        → 0.611
```

スコアレンジが 0.59〜0.69 と非常に狭く、「ほぼ同文」と「無関係」の差が 0.1 程度しかない。有効な閾値を設定できない。

**根本原因**  
このモデルはクエリ—ドキュメントの検索リランキング（情報検索）用途で設計されており、会話文同士の意味的類似度判定には適していない。

**今後の代替候補**
- 日本語 STS（Semantic Textual Similarity）専用の cross-encoder が必要
- `hf_models.py` の `cross_score()` 関数はそのまま残してある

---

### 4. NLI（自然言語推論） ❌ 統合見送り

**モデル**: `Formzu/bert-base-japanese-jsnli` (~110MB)

**入れようとした理由**
- `EventIntentClassifier` のプレスクリーニング — 明らかに雑談であれば LLM 呼び出しをスキップ
- 「contradiction が高い」→ `is_event_intent: false` として LLM 不要

**入れなかった理由（実験結果）**

仮説: 「具体的な行動や活動を提案または計画している。」

```
明日みんなでカレーを作ろうと思う！    → entailment=0.77 ✓（True）
誰か材料を買ってきてくれない？役割も決めよう → 0.68 ✓（True）
そうだねー（雑談）                  → 0.32 △（None — LLMへ）
うん、楽しそう！（雑談）              → 0.20 △（None）
一緒に映画を見に行かない？（明確な提案）→ 0.10 ✗（Falseになる誤判定リスク）
```

「一緒に映画を見に行かない？」のような勧誘文が entailment=0.10 になるなど、**偽陰性リスクが高い**。EventIntentClassifier で False を返した場合、LLM が判定できたはずのイベントを見逃すことになる。

**結論**  
NLI は「True（イベント）」の確認には使えるが「False（非イベント）」の確定には使えない。LLM スキップの用途には不適切。

**今後の活用可能性**
- 矛盾検出（直前の発言と今の発言が矛盾しているか）
- トピック一貫性チェック
- `hf_models.py` の `nli_classify()` / `is_event_proposal()` 関数はそのまま残してある

---

## まとめ

| モデル | 統合 | 判断の決め手 |
|---|---|---|
| 感情分析 BERT | ✅ | テストで正確に動作、ユースケースに合致 |
| T5 要約 | ❌ | ベースモデルのため会話要約の品質が低い |
| Cross-Encoder | ❌ | スコアレンジが狭く弁別不可（用途ミスマッチ） |
| NLI | ❌ | 偽陰性リスクが高く分類器として信頼できない |

4モデルすべてのコードは `hf_models.py` に実装済み。将来より適切なモデルが登場した際は差し替えのみで対応可能。
